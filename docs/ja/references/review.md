# レビューループ、エビデンス、納品

静止画一枚ではリズムは分かりません。変更のたびに：`vfx lint`、`vfx build --ids <ID>`、`vfx review --ids <ID>
--note "<one problem, one change>"`（問題一つ、変更一つ）を実行し、それから **画像を開きます**。

目次：レビューが出力するもの · フラグ · ストリップの読み方 · ラウンドと履歴 · 独立レビュー ·
検証 · バリエーション · 撮影時の挙動

## `vfx review` が出力するもの

Godot Lab は、UI を隠した実 viewport で、対戦演出（プラットフォームの両端に立つ 2 体のダミー。エフェクトは `delivery` に従って演出される）を使ってエフェクトをレンダーします。
フレーム番号はエフェクト自体の開始（パンチ、詠唱、飛翔体の到達）から数え、ダミーは待機ポーズを保ちます。飛翔体のストリップは到達で終わり、
着弾は含みません。着弾のストリップは同じ着地点と到達時刻を保ちますが、飛来する飛翔体の残りは含みません。コマンドは次を返します。

- `sheets` — タイムライン全体のストリップ `vfx/previews/strips/<ID>.png`（最大 18 タイル。キーフレームは決して間引かれません）
- `compare` — 前のストリップがある場合の `<ID>_compare.png`。上が前のラウンド、下が現在のラウンド
- `details.<ID>.sheet` — キーフレームシート（接触の前後、ブリーフの beats、本体、退場、duration 後のチェック）、
  そして `details.<ID>.frames` — フルサイズのフレーム
- `flags`、`changes`（前のラウンドから追加・解消されたフラグの種類、動いたキータイミング）、`metrics`、
  `history`、そしてこの撮影の `evidence` ID

`vfx strip <ID> [--compare]`、`vfx frames <evidence_id> <frames...>`、`vfx history <ID>` で後から読み直せます。
比較画像がある場合は、まずそれを見てください。

## フラグ

ピクセル指標は空のステージに対する「変化エネルギー」なので、大きく淡い煙と小さな白いフラッシュを比較できます。読み取りの補助であって、
GPU やオーバードローの計測では **ありません**。

| フラグ | 意味 | 最初の修正 |
|---|---|---|
| `barely visible` | 最も強いフレームでステージの 0.25 % 未満しか変化していない | 本体が小さすぎるか暗すぎる |
| `dead tail` | 最後の 35 % に、ピークエネルギーの 5 % を超えるフレームも、ステージの 0.25 % 以上が変化したフレームもない | `duration` と後続のライフを短くするか、消散を見えるようにする |
| `blown out` | サンプリングした 2 フレームを超えて、10 % 以上が純白 | グローを小さく、エミッシブを下げる |
| `cut off` | 最後のフレームでまだはっきり見えている | duration が短すぎる |
| `off-peak contact` | 最も白いフレームが、マニフェストの `peak` から 6 フレームより離れている | 接触か `peak` を動かす。Lab のフラッシュとキックが別の場所に着地している |
| `lingering flash` | 接触付近でピーク近くの白が 12 フレームより長く続く | 接触は 2〜5 フレームにする。持続する熱い本体（ビームのコア、棘）は対象外 |
| `no white-hot core` / `washed out` | ピークで明るさ 85 % を超えるピクセルがほとんどない / 高彩度の中間調の本体がほとんどない | 熱いコアを足す / 本体の彩度を戻す |
| `sinks`（炎のみ） | 接触後に塊が下へ動く | 炎は昇るべき |
| `expands while charging`（闇のみ） | 解放前に半径が大きくなる | 闇は内側へ引き込むべき |

しきい値は、実際のライブラリのレンダーでタイルごとに調整したもので、その理由は `scripts/vfxkit/review.py` の冒頭にあります。
しきい値を変えるのは実際のストリップを確認した後だけにし、そこに理由を一行追記してください。

## ストリップの読み方

フラグだけではレビューになりません。ストリップとキーフレームシートで次を問います。

1. 最初に光ったタイルで、それが何のエフェクトか分かるか？ 接触が最も明るい瞬間で、数フレームだけか？
2. メインの形は侵食・スイープしているか、それとも拡大とフェードだけか？
3. 二次パーティクルは速いから遅いへ、属性の方向（炎は上、氷は下、闇は内側）へ動いているか？
4. 弧、柱、地面のデカールが、ダミーの横や宙に浮かずに、ダミーの上または足元にあるか？
5. 明るい背景（`--bright`）でも、アルファブレンドのレイヤーは機能しているか？

テールは最後の 2 タイルだけでなく、最後の 3 分の 1 の中ほどを見ます。実際のフレームは `vfx frames` で取得するか、
`--key-frames` で追加の瞬間を撮影します。孤立した煙のひと吹きが一つあるだけでは、退場全体の証明にはなりません。

## ラウンドと履歴

各ラウンドでは **1 種類の問題** を直し、それを `--note` に書きます。メモ、フラグ、キータイミングは
`vfx/previews/strips/history/<ID>.jsonl` に追記されます。新しいラウンドの前に履歴を読み（`vfx effect-context <ID>`）、
エビデンスがすでに退けた変更を繰り返さないでください。エフェクトごとに 3〜5 ラウンド反復し、上限に達しても合格しなければ、
完了とは言わずに未解決の項目を報告します。

## 独立レビュー

作者は自分のエフェクトを採点しません。`vfx review-handoff <ID>` は、鮮度が保たれた最新の撮影について、レビュアー向けのブリーフ一式を
`vfx/work/handoff/<evidence_id>.md` に書き出します：ストリップとキーフレームの画像、撮影したフレーム番号、マニフェストのエントリとフラグ、
評価基準のコピー、このスキルの隣にインストールされていれば **vfx-review** スキルのパス、そしてレポートの書き込み先です。
そのブリーフだけを別のエージェントに渡し、それ以外は何も渡しません：サブエージェント（ブリーフ以上のことは伝えない）か、
ホストにサブエージェントがない場合はユーザーが開く新しいセッションです。レシピのコードは渡しません。レビュアーは JSON を `report_file` に書き込みます。

```json
{"id": "VFX_X", "scores": {"read": 2, "timing": 3, "layering": 2, "shape_change": 2, "motion": 2, "placement": 3, "tail": 2, "identity": 3},
 "worst": "shape_change", "fix": "one concrete change in recipe terms", "verdict": "ship"}
```

`fix` にはレシピの言葉で具体的な変更を一つ書きます。いずれかのスコアが 2 未満なら `verdict` は `iterate` で、`worst` は最低スコアの項目でなければなりません。
それをファイルに保存し、`review-handoff` が返したコマンドで結び付けます：`vfx review-submit <evidence_id> <report_file> --reviewer <reviewer id>`
（`--frames` の既定値はレポートの `observed_frames` です）。
ツールは構造、鮮度、観察したフレームを検証しますが、レビュアーの独立性は証明できません — ホスト（あなた）が実際に隔離しなければなりません。
判定が `iterate` なら、次のラウンドでその一つの修正を適用します。

## 検証

`vfx overview` は、最新の標準撮影を並べて `vfx/previews/strips/overview_*.png` を作ります。
`vfx effect-verify <ID>` は、展開した現在のレシピ、入力テクスチャ、Core の読み戻し、ビルドしたリソース、Lab のステージ、画像が、
すべて合格したレビューが見たものと同じであること、そして総覧にこの撮影が含まれていることをチェックします。完了は `verified: true` だけです。
スクリーンショットが存在すること、フラグがないこと、終了コード 0 は、品質の合格ではありません。レシピ、テクスチャ、ブリーフ、Lab の
どれかを変更すると古いエビデンスは無効になります。Lab のテンプレートを更新した後は、まず `vfx init --update-templates` を実行します。
ランタイムの挙動には独自の API チェックが必要で（`TestApi.gd`、[godot](godot.md) を参照）、デバイス性能にはデバイスでのエビデンスが必要です。

作業を終えたら、エフェクトライブラリ（`vfx/src`、`vfx/briefs`、テクスチャ、レシピ JSON、`.efkefc`、`.efk`、
マニフェスト、総覧ページ、`metrics.json`）をまとめてバージョン管理に入れます。フレームごとの撮影、ログ、レシート、
単一エフェクトのストリップはローカルに留めます（`init` が書き出す `vfx/.gitignore` がこれを処理します）。

## バリエーション

`--view close` は確認用のカメラだけを変えます。`--profile bare` は Lab のブルーム、インパクトライト、カメラキックをオフにして、
エフェクト単体で判断できるようにします。`--bright` は明るい背景を使います。それぞれ別々に保存され、標準/既定（standard/default）の
ベースラインやその指標を上書きすることはありません。検証のベースラインは standard/default です。

## 撮影時の挙動（macOS / Windows）

レビュー中もユーザーがマシンを使っていることがあります：macOS は完全に覆われたウィンドウの描画を止め、Godot は起動時にフォーカスを奪います。
撮影モードの Lab はウィンドウを最前面に保ち、右下隅に寄せて一部だけを見せ（viewport は 1280×800 でレンダーされ続けます）、
キーボード入力とクローズ要求を無視し、レビューはフォーカスを直前のアプリに戻します（起動ごとに約 0.2 秒のちらつき）。
早く退場してしまったり、まったく再生されなかったりしたエフェクトは、撮り直されます（最大 3 回）。

Windows では、Lab は同じようにウィンドウを寄せますが、レビューはフォーカスを戻しません。撮影が終わるまで Godot ウィンドウが
フォーカスを保持します（エフェクト 2 つのレビューなら 1 分もかかりません）。撮影中は最小化しないでください。
